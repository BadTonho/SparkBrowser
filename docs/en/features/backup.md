# Local backup and reviewed import

The optional boolean `auto_skip_ads_enabled` preference is also included. Older backups default it to false; reviewed preference application updates both its local storage and running policy. Data-only import keeps the local auto skip choice. See [Auto skip ads](auto-skip-ads.md).

The keyboard shortcut contract includes the Picture-in-Picture action and is checked against the interface's default action list.

Settings → Data & Backup exports a versioned `.spark-backup.json` file through the system file selector. Desktop builds support this feature; browser preview shows it as unavailable. The format is `spark-backup`, version 7, limited to 32 MiB. Versions 1–6 remain importable. Version 7 adds `device`, the name of the computer that wrote the file (shown in the sync panel; not part of the fingerprint, so the same data from two computers is the same backup). An older Spark cannot read a version 7 file until it is updated. Version 6 adds the settings display preference; older files default to pop-up. Version 5 adds an integrity checksum (see [Backup integrity and versions](backup-integrity.md)). Version 4 adds the left/right split tab groups and remaps every member when importing a new workspace; legacy splits put other tabs on the left. Version 2 introduced optional site zoom preferences; existing local origins win on conflicts. Version 3 adds the boolean `pip_window_shadow` preference, defaulting to `false` when absent. It applies only when **Apply preferences from backup** is checked; importing data alone leaves the local shadow choice unchanged. No cloud service is involved.

Backups contain bookmarks/folders, workspaces/colors, named sessions, plain-text notes, keyword searches, open tab order/pins/selection, split layouts and persistent interface/navigation/hibernation/language/keyboard/update-channel preferences. Cookies, password storage, native site permissions, history, recently closed tabs, download records/files and signing keys are excluded. Page forms, scroll position and internal navigation history are not snapshots. Page URLs must be HTTP/HTTPS without embedded credentials; browser tabs may also contain the exact internal new-tab and settings addresses.

Export flushes pending notes and navigation writes, captures a consistent database/session snapshot and writes to a temporary file in the destination directory. The complete file is synced and atomically replaces the chosen destination. Validation or write failures retain the previous backup. Use a filename ending in `.spark-backup.json`; paths are never silently changed after overwrite confirmation.

Import first shows counts, additions, skipped conflicts and preference values. **Apply preferences from backup** starts unchecked. Workspace/folder names match without case sensitivity; bookmark/note URLs and search keywords identify existing data. Current values win. Identical session contents are skipped; different sessions with the same name receive a unique suffix. Notes ignore URL fragments while keeping query parameters.

File selection retains one validated document in the native backend and returns an opaque selection token. The interface receives preview summaries and preferences. Replacing or canceling a selection, or completing its import, releases the retained document. Stale-preview validation uses a streamed SHA-256 digest of current data/preferences rather than retaining another serialized copy. Structured programmatic imports remain supported.

Current tabs keep their IDs, order and selection. The importer compares URL occurrence counts within each workspace and appends only missing occurrences with fresh IDs, preserving intentional duplicates. New tabs remain hibernated. Split pairs are remapped only for newly created workspaces; existing layouts stay intact. Reimporting the same backup does not add duplicates.

A preview is bound to the current data and preferences. If they change before confirmation, refresh the preview. Data and the optional preference task commit in one SQLite transaction. Preferences apply afterward; failures leave a persistent pending task and a retry button, including after restart. Retry applies preferences without importing data again. Complete a pending task before importing another set of preferences. Backup files and temporary exports are ignored by Git.

Rust tests cover file roundtrip, invalid versions/references/size, atomic replacement, conflict rules, occurrence counts, ID/split mapping, transaction rollback and preference retry isolation. `npm run test:native -- --case backup` exercises actual commands, stale previews, hibernation, repeated import and persistence after restart. Native file selection uses the [Tauri dialog plugin](https://v2.tauri.app/plugin/dialog/) from Rust without granting its JavaScript file/dialog commands.

## How the page is organized

**Settings → Data & Backup** has three categories, each with a title, in this order:

- **Sync**: a standing card with the Drive icon, the name of the sync mode in use (Google Drive, Folder, WebDAV, or "Sync is off") and its state. Select it to open the sync settings, which are split into parts with a title: **Account** (Google Drive), **Folder** or **Connection** (WebDAV); **Automatic**, with switches like the rest of Settings, each with a line explaining it; and **Sync now**, where **Send**, **Review** and **Apply** each say what they do. It comes first because it is what most people check. Under **Frequency and pause**, choose how often changes are sent (automatic: every change for a folder, every minute for Google Drive and WebDAV; every 5 or 15 minutes; or only when the browser closes) and pause automatic sending for an hour or until tomorrow (nothing is sent on its own until then, not even when closing; **Resume** ends the pause). **Sync now** says when the file in the cloud was sent and by which computer. If automatic sync fails 3 times in a row, a notice with **Open** appears outside Settings, once per streak. **Download when Spark opens** (under **Automatic**, every mode) reads the file in the cloud before anything is sent (`sync_backup_on_start`). It compares three fingerprints: the file's, this computer's data now, and the one recorded at the last send or apply. The same as last time: nothing happens. Only the cloud changed: the file is applied like **Apply directly** and a notice names the computer it came from. This computer changed too (or nothing was ever synced here): the review opens instead, with a notice to review it, and nothing is applied on its own. An empty cloud is not an error. A pause also stops it. **What syncs** turns each group on or off for this computer (workspaces and tabs, bookmarks, saved sessions, notes, site search, settings, shortcuts; at least one stays on). A file sent from here only carries the data of its groups, applying from the cloud only touches them, and fingerprints only cover them (`sync_filter.rs`), so two computers that sync different groups still agree when nothing they share changed. Preferences always stay in the file because the format needs them; the receiving computer applies them only if it syncs settings or shortcuts. **Earlier versions** lists older copies of the file in the cloud and opens one in the review panel, so nothing changes until it is confirmed there (`list_backup_sync_versions`, `review_backup_sync_version`). Google Drive keeps revisions of the same file on its own (usually for 30 days), which the hidden Drive page lists and downloads (`__sparkGDriveVersions`, `__sparkGDriveVersion`; revision ids are checked on both sides). For a folder or WebDAV, before a changed file replaces the current one, the current one is copied to a `versions` folder next to it as `browser.spark-backup.<unix seconds>.json` (WebDAV uses MKCOL, COPY, PROPFIND and DELETE) and the newest 5 stay (`sync_versions.rs`). Version names are parsed before they reach a path or URL, and failing to keep a version never stops a send (it is logged). These choices are saved apart from the target (`set_backup_sync_options`), so changing them never touches the account or the saved password. Like the download button, its border shows a ring: green and filling while a sync runs (manual or automatic), green and full for about 2 seconds when it finished, yellow while automatic sending is off or Google Drive waits for an account to be chosen, and red after an error. The ring is drawn with CSS classes only, because projected settings drop inline styles and SVG attributes.
- **Automatic backups**: the status of the backups on this computer, the schedule, encryption and the history (see [Automatic backups, history and encryption](backup-automation.md)).
- **Backup files**: **Full backup** (export a backup file or choose one to restore) and **Favorites** (export to HTML or CSV for another browser). The password prompt for an encrypted file, the import preview, errors and results appear right below these cards.

## Isolated automatic sync (Google Drive Cloud, Folder & Direct WebDAV)

Settings → Data & Backup also includes **Isolated Automatic Sync**, allowing users to keep `browser.spark-backup.json` synchronized using their own storage with zero Spark servers or developer cloud console accounts:

1. **Google Drive in the cloud mode (uses browser Gmail login):**
   - Uses the browser's signed-in Google/Gmail session cookies (`drive.google.com`) to automatically create/locate the dedicated **`Spark Backup`** folder in `My Drive` and upload/download `browser.spark-backup.json` inside it, without requiring a local folder on the PC or a Google Cloud Console developer project. When pulling, if the file is not yet inside `Spark Backup`, it also checks the `My Drive` root for backwards compatibility.
   - Displays the currently connected Google account email (`connected_account`) and provides a **Choose or switch account** button that opens Google's `AccountChooser` (`accounts.google.com/AccountChooser`) and automatically syncs as soon as the chosen account's Google Drive tab loads.
   - When automatic saving is enabled, a 1-minute timer checks the streamed SHA-256 fingerprint of current data and preferences and uploads to Google Drive **only when changes occurred**, in addition to syncing on browser shutdown and via **Send to the cloud** (under **Sync now**).
2. **Synced folder mode (OneDrive, Mega, Dropbox, USB drive):**
   - The user chooses a local directory via the native folder selector (`choose_backup_sync_folder`).
   - When automatic saving is enabled, changes to bookmarks, workspaces, tabs, split layouts, notes, shortcuts or preferences write `browser.spark-backup.json` atomically into the selected folder, as well as on browser shutdown and via **Send to the cloud** (under **Sync now**).
3. **Direct connection mode (WebDAV / Personal cloud):**
   - The user configures an `https://` WebDAV URL (loopback `http://127.0.0.1` / `localhost` is permitted only for local testing), username and app password/token.
   - Users can choose whether to **remember the password on this computer** (Windows Credential Manager or the Linux Secret Service through `secret-tool`) or keep it **only in memory for the current session**.
   - When automatic saving is enabled, a 1-minute timer checks the streamed SHA-256 fingerprint of current data and preferences and uploads (`PUT`) to the WebDAV target **only when changes occurred**, in addition to syncing on browser shutdown and via **Send to the cloud** (under **Sync now**).
   - **Nextcloud** is this mode with a sign-in: the person types only the server address and allows Spark on the server's own login page, and Spark saves the account's `Spark` folder with an app password made for it. See [Sync with Nextcloud](nextcloud-sync.md). An S3-compatible mode is [planned](../roadmap/s3-sync.md).
4. **Two receive modes (`pull_backup_sync`):**
   - **Review before applying:** downloads/reads the backup and opens the standard review table before importing.
   - **Apply directly:** validates and merges the backup immediately in a single step, optionally applying backup preferences when enabled.
5. **Zero-leak boundary:** Sync folder paths, WebDAV endpoints and credentials are local-only settings and are never serialized into `BackupDocument`.

## Import and account safety

Import preserves all existing live tabs, including disposable tabs, their order, active selection, split membership and account-container identity. Existing identities remain intact in the SQLite transaction; imported tabs use the default identity because backups exclude account-container data.

Drive synchronization requires the explicit **Choose or switch account** flow. It binds the selected persistent profile and account index and verifies the detected email before transfer. Disposable tabs and unrelated active profiles are never fallbacks. If the chosen profile has no resident tab on Windows, reopen a tab in that profile. Existing installations must choose their Google account once after upgrading.

Remembered WebDAV passwords never enter new SQLite preference values. Linux requires `secret-tool` (the `libsecret-tools` package on Debian/Ubuntu) and an unlocked Secret Service provider. Storage errors are reported without plaintext fallback. Legacy SQLite passwords are removed with secure deletion enabled and migrated to the system store on startup; if migration fails, they remain only in process memory for that session. Historical database copies and backups cannot be erased by this migration. Changing the WebDAV server or username does not reuse the previous target's password.

Files saved under the old Veloce name (`.veloce-backup.json`) still import; see [Upgrading from the Veloce name](rename-migration.md). To move bookmarks to another browser, see [Bookmark export for other browsers](bookmark-export.md). See [Backup integrity and versions](backup-integrity.md) for the checksum and how older files are upgraded, and [Automatic backups, history and encryption](backup-automation.md) for scheduled snapshots, restore from history and password protection, and [Selective restore and replace mode](selective-restore.md) for choosing what a restore touches.
