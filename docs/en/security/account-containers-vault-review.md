# Account containers and password vault: feasibility and security review

Status: **account-container implementation under validation; first vault release shipped without an independent audit**. The password vault described in [Password manager](../features/password-manager.md) accepts real credentials, by the owner's explicit decision, behind a permanent in-app notice that it has not been independently audited. The audit gate below is **still open**: it was not performed, and this document is an audit input, not an audit or an approval. No independent reviewer has been engaged through this work.

## Container feasibility gate

Explicit account containers are intended to share one persistent identity across tabs and workspaces, including when workspace isolation is enabled. Ordinary tabs retain their current profile selection; ephemeral tabs remain disposable. Switching identity must destroy the old content WebView before a new one loads, and deletion must close all users of the identity and confirm removal of its data. Failed removal must be reported and retried, not presented as successful deletion.

The content WebView uses Tauri's `data_directory` selected in `workspace_data.rs`. Explicit containers take precedence over opt-in workspace isolation; ephemeral directories take precedence over both. Settings → Workspaces provides container creation, rename, deletion, opening a tab and assigning the active tab. Deletion closes affected WebViews, detaches their tabs, and marks a failed deletion for retry. Backups and named sessions do not include container identity or website data; restoring them opens their tabs in the default identity. [Tauri documents the data directory](https://docs.rs/tauri/latest/tauri/webview/struct.WebviewBuilder.html#method.data_directory); [Microsoft documents WebView2 profiles and user data folders](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/overview-features-apis?tabs=win32cpp). API availability alone does not establish isolation, persistence, cleanup, or race behavior.

The native `account-containers` scenario uses a local HTTP fixture to check cookies, localStorage, IndexedDB, identity sharing across workspaces, separate/default identities, ephemeral tabs, switching, restart and deletion. Additional tests are needed for popups, split views and locked-file failure. Run the scenario on both platforms when available, record engine versions and results, and do not claim platform verification from an API or a unit test.

## Proposed vault security boundaries

- The vault is local. A master password is required to initialize it; optional OS-assisted unlock is an additional wrapping mechanism, not a replacement for recovery. An offline recovery key is generated with a cryptographically secure random source and shown once for the user to retain. Losing both the password and recovery key can make data unrecoverable. Rotation, revocation, export, and crash-safe replacement require audit before selection of a persistent format.
- Use a random data-encryption key and independently wrapped copies for password, recovery and optional OS unlock. An independently reviewed implementation must choose and parameterize a memory-hard password KDF and authenticated encryption, bind metadata/version to ciphertext, use unique nonces, protect against tampering and perform atomic durable writes. The design, libraries, parameters, migration and rollback protections remain audit decisions; this model implements none of them.
- The OS mechanism must protect a wrapping secret and fail closed if unavailable, locked, deleted or changed. Windows credential-manager code currently serves a separate Gmail integration; it does not establish biometric or user-presence authentication. The non-Windows implementation reports secure storage unavailable for writes. Neither is an approved vault backend. No plaintext fallback is allowed.
- A trusted browser UI explicitly requests save or fill; no automatic fill or page-provided command can unlock or enumerate credentials. Bind each entry to a canonical scheme, host and effective port. Require HTTPS for real credential operations, except test fixtures isolated from production. Treat subdomains, different ports, redirects and embedded frames as different origins unless separately authorized. Recheck the active tab, WebView generation, committed top-level document and destination origin immediately before delivering a selected secret; invalidate pending actions on navigation, lock or WebView replacement. Cross-origin frames are denied pending a separately audited design.
- Web content is untrusted. Restrict privileged commands to the trusted application UI, validate every request in the backend, and never expose vault keys or an enumeration API to content pages. Filling necessarily exposes the selected value to the destination page and cannot protect against a compromised matching site. The browser must make that trust boundary explicit.
- Lock on user request and on application exit; define automatic lock and OS-lock behavior during implementation and audit. Minimize secret lifetime in memory and clear buffers where feasible, without claiming guaranteed erasure. Never log credentials, keys, recovery material or decrypted data; exclude them from existing backups, diagnostics and crash artifacts. Handle errors without revealing secrets. Protect against concurrent writes and interrupted updates.

Threat review must cover malicious pages and frames, stale documents, compromised UI/IPC, offline theft or tampering, unauthorized OS-session access, recovery-key theft, clipboard exposure, key rotation, backup leakage and denial of service. Malware or a compromised process running as the user while the vault is unlocked remains a residual risk. Audit must evaluate KDF cost, memory handling, side channels, origin canonicalization, storage and lifecycle on both systems.

## Fixture model and audit gate

`tools/testing/vault-model.mjs` is a test-only candidate exercised by `tests/vault-model.test.mjs`. It encrypts fixed synthetic records with AES-256-GCM and derives fixture wrapping keys with scrypt. It uses in-memory storage and a simulated OS adapter, accepts no real credential input, and has no production UI or page bridge. Tests cover reopening, recovery, corruption, selection, simulated origin changes and failure paths. These are not evidence of production security, actual OS integration, disk durability or origin enforcement in the browser. Algorithms and parameters are examples for review, not approved production choices.

Before real credentials are accepted: implement an isolated candidate; test real cryptographic and platform integrations with synthetic data; obtain an independent security audit covering the threat model and code; address findings and obtain a recorded review of fixes; then separately decide activation. The model and these notes must not be presented as a completed audit.

## First vault release (Settings → Passwords)

Decision: the project owner chose to implement the vault and ship it with a permanent notice ("Not independently audited yet") instead of waiting for the audit. Nothing in this section is an audit result.

What was built, against the boundaries above:

- **Local, master password required.** A random 256-bit data key encrypts every entry with AES-256-GCM (random nonce per write, entry id and format version bound as associated data). The key is wrapped twice with keys from Argon2id (64 MiB, 3 passes, bounded on read): once from the master password and once from a 160-bit recovery key shown once at creation. Changing the master password rewraps the key only.
- **Not done in this release:** optional OS-assisted unlock (the Windows credential store and `secret-tool` were not used, matching the review above), recovery-key rotation, export, and the independent audit of KDF cost, memory handling, side channels and crash-safe replacement.
- **No page integration.** There is no autofill, no save prompt and no page-facing API, so the origin-binding, active-tab and WebView-generation checks listed above do not apply yet and **must be designed and audited before any page integration**.
- **Lock behavior.** Manual lock, idle lock (1 to 60 minutes, default 5) and lock on exit; the key exists only in memory and is wiped with `zeroize` when dropped. The OS-lock event is not handled.
- **Brute force.** After 3 wrong attempts each further attempt waits (doubling, capped at 60 s). This slows the interface only; it does not protect against offline attacks on a copied database, where the Argon2id cost is the defense.
- **Isolation.** Only the shell interface can call the vault commands; private windows refuse them; the tables are excluded from backups, sync and private profiles; failures are logged without secret material.
- **Known residual risks.** Secrets are plain strings while they cross the interface and the clipboard; zeroization is best effort; malware running as the user while the vault is unlocked can read it; the clipboard is cleared after 30 seconds but other programs may read it earlier; the encrypted file can be copied and attacked offline.
