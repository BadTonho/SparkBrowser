# Integração nativa local

As verificações de widgets em `new-tab` usam fixtures de clima, busca de cidades e Gmail/OAuth em loopback. Elas verificam PKCE, rejeição de estado OAuth incorreto, cancelamento, respostas da caixa atrasadas após desconectar, requisições compartilhadas entre painéis do split, conversão de unidade sem nova consulta, empilhamento na largura mínima, texto seguro das mensagens, preservação de rascunho/foco, rollback de falha na gravação e persistência após reiniciar. Endpoints de fixture são aceitos somente pelo aplicativo isolado de testes e nunca acessam o cofre de credenciais de produção. Consentimento real de localização no Windows, persistência segura de credenciais e autorização de uma conta de teste Google exigem verificações manuais; consulte a [configuração dos widgets](../features/new-tab-widgets.md). Preferências dos widgets, localizações e dados de conta ficam fora dos backups de versão 4.

A validação local usa os comandos em [validação](validation.md). No CI as suítes nativas executam apenas manualmente (`native.yml`); rode-as localmente antes de uma release. Consulte o [fluxo de regressões](regression-workflow.md). O aplicativo isolado é exercitado pelo [WebDriver do Tauri](https://v2.tauri.app/develop/tests/webdriver/).

## Execução isolada no Windows

Instale Node 24, Rust estável e os pré-requisitos normais do Tauri; depois execute na raiz do repositório:

```powershell
npm ci
cargo install tauri-driver --version 2.1.0 --locked --root .cache/native-tools
./tools/testing/install-edge-driver.ps1
npm run test:native:build
$env:SPARK_NATIVE_DRIVER = '.cache/native-tools/edge/msedgedriver.exe'
npm run test:native
```

O instalador do driver Edge acompanha o runtime WebView2 instalado. As builds usam `.cache/native-target` e o identificador `org.spark.browser.native-tests`. Cada cenário recebe um diretório novo em `.cache/native-runs/`, com pastas separadas `data`, `profile`, `config`, `cache`, `logs` e `artifacts`. Reinícios dentro do cenário reutilizam esses caminhos. Somente o identificador de testes aceita `SPARK_NATIVE_TEST_RUN_DIR`, restrito a essa raiz; a versão de produção o ignora. O executor verifica identidade e diretório de dados antes de alterar estado.

Para iteração local, `npm run test:native:build:fast` usa um build isolado menos otimizado; execute novamente `npm run test:native:build` para validação com o perfil de release. Os metadados do build registram o perfil utilizado.

O cenário Windows `account-containers` ativa `SPARK_NATIVE_REAL_PROFILES=1` somente no aplicativo isolado. Antes de criar o runtime, ele remove a variável `WEBVIEW2_USER_DATA_FOLDER` definida pelo EdgeDriver, que normalmente [tem precedência sobre o diretório de cada WebView](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/webview2-idl). Os processos de perfis separados informam valores sintéticos de cookies, localStorage e IndexedDB pela fixture local, enquanto o WebDriver controla a interface principal. O teste aguarda o documento inicial e o encerramento normal dos processos de perfil, então confere o armazenamento novamente após reiniciar. A contenção dos diretórios usa caminhos canônicos; no Windows, as APIs nativas recebem caminhos convencionais de unidade. Os demais cenários do driver cobrem interface e sessão no perfil escolhido pelo driver; eles não comprovam isolamento do armazenamento. A produção ignora ambas as variáveis exclusivas dos testes nativos.

Use `npm run test:native -- --list` para listar os cenários ou `npm run test:native -- --case notes` para executar um. Sem argumentos, todos são executados de forma independente, continuando após falhas. Seletores estáveis `data-testid` independem do idioma da interface. As portas padrão são 4444/4445; use `SPARK_DRIVER_PORT` para outro par livre.

A limpeza executa em `finally`, encerra somente a árvore do processo de driver do cenário e remove data/profile/config/cache/logs mesmo após falha. Relatórios e capturas de falha permanecem em `artifacts`. Erros de limpeza são registrados sem substituir a falha original. Defina `$env:SPARK_NATIVE_FAIL_CASE = 'notes'` para provocar uma falha após o cenário e verificar a limpeza; remova a variável depois. `SPARK_NATIVE_SCREENSHOTS=1` também preserva uma captura das atualizações no cenário de diálogos.

A suíte usa páginas HTTP locais e verifica preservação de abas/formulário/rolagem, histórico SPA, shield, rascunhos de endereço, diálogos, resize e restauração de sessão. Também exercita sessões nomeadas, codificação de buscas, notas, fechamento em lote protegido, substituição/fechamento/restauração da divisão e pedidos nativos de permissão. Processos de teste no Windows recebem `--use-fake-device-for-media-stream`; verificações de microfone usam um dispositivo simulado. Cenários de permissões cobrem decisões temporárias/lembradas, redefinição, cancelamento ao navegar, origens incorporadas e persistência após reinício. Os testes usam comandos existentes e handlers reais do DOM, sem permissões IPC exclusivas de teste.

As verificações de regressão do seletor de workspaces registram transições de visibilidade das páginas nativas: abertura, fechamento, reabertura rápida e reconciliação com limite baixo de residentes devem preservar a página por trás do seletor, incluindo os dois painéis da divisão. Valores de formulário, rolagem e contagens de carregamento dos documentos devem permanecer iguais. Diálogos da interface ainda devem ocultar e restaurar ambos os painéis.

O executor direto também aceita instalações Linux de `tauri-driver`/WebKitWebDriver pelas variáveis `SPARK_TAURI_DRIVER` e `SPARK_NATIVE_DRIVER`; esse caminho ainda não foi validado localmente. O macOS precisa de um serviço WebDriver embarcado separado. Transições de DPI entre monitores, gestos de arraste além do encaixe de abas, latência de renderização e memória agregada dos processos ainda precisam de validação específica.

No Windows, o encaixe usa entrada nativa do ponteiro porque o WebDriver pode perder a captura ao cruzar WebViews filhas. O helper confere o executável isolado, a janela em primeiro plano e o ponto inicial, limita os destinos à área cliente e registra a liberação do botão mesmo após falhas. F7 usa o helper existente de teclas nativas para exercitar o acelerador do WebView2; teclas enviadas somente ao DOM não testam esse acelerador. O Linux mantém a entrada pelo WebDriver.

F7 e a confirmação no primeiro uso recebem pressionamentos nativos completos: pressionar e soltar executam no mesmo processo auxiliar para que sua inicialização não gere repetições de tecla mantida. A entrada na confirmação fica restrita ao perfil WebView2 verificado do cenário. As verificações limpam seleções anteriores antes de testar o modo de cursor desligado. Os helpers de foco selecionam temporariamente a interface privilegiada e restauram o destino anterior do WebDriver. A seleção da janela principal no Windows exclui diálogos nativos e janelas internas de eventos do Tao, inclusive quando minimizada. O resultado de um único pedido de ativação é observado por até dois segundos; uma falha continua reprovando o cenário.

Os cenários de transferência desativam explicitamente a pergunta de destino na preferência isolada e na política nativa, mantendo essa configuração após reiniciar. Assim, diálogos Salvar como ficam fora dos testes que verificam progresso automático e foco do painel; o padrão de produção permanece igual. Cenários nativos com interface precisam do desktop sem interrupções: comandos de terminal concorrentes ou a ativação de outro aplicativo podem fechar os painéis legitimamente. Diagnósticos locais registram metadados de foco do DOM e a identidade do processo em primeiro plano, sem coletar títulos de janelas externas. O rastreamento temporário de foco fica fora do código do aplicativo e dos artefatos publicados.

O cenário `recovery` interrompe seu próprio processo de teste, verifica todas as abas e o foco da divisão e depois confere um reinício normal. `recovery-failure` injeta um trigger SQLite somente no banco do cenário encerrado e com identidade verificada, comprova que a falha de inicialização mantém o snapshot anterior, remove o trigger e tenta novamente. Os cenários `closed-tabs` e `backup` cobrem reabertura e importação revisada com novas tentativas persistentes de preferências.

A suíte também inclui `downloads` (checkpoints duráveis, intervalos HTTP, integridade e controles nativos), `shutdown` (gravação de notas, revisão de novos riscos, cancelamento e falha SQLite), `tab-diagnostics` (residência real e proteção revalidada), `zoom` (escala das páginas residentes, origens, navegação, atalhos, reinício e preferências do backup) e `command-search` (resultados Unicode limitados, seleção estável, URLs originais das notas e detalhes revisados de sessões). Os downloads dos testes gravam exclusivamente em `data/downloads` do cenário, sem usar a pasta pessoal de Downloads. Use `npm run test:native -- --list` para consultar os cenários atuais. No Windows, `keyboard` envia entrada real somente ao executável isolado em primeiro plano e verifica fechamento/reabertura de abas consecutivas mantendo modificadores pressionados; mantenha o desktop de teste disponível. Ela não executa instaladores nem usa VM.

## Medições

`downloads-list` confere o formulário recolhido por padrão, preservação do rascunho, foco nativo, envios inválidos/vazios, reticências em uma linha e prévias de 40 px. Downloads controlados de PNG/JPEG/GIF/BMP devem gerar miniaturas nativas locais; arquivos corrompidos/incompatíveis/removidos usam ícones. Também testa a consulta visual por tarefa/histórico, referências inválidas e rejeição do documento auxiliar. Os controles de integridade não aparecem mais no painel compacto; os testes de transferência configuram hashes pelo comando protegido existente.

`downloads-popover` confere o cartão opaco de 480 px ancorado, altura do conteúdo, rótulos compactos de tamanho, ações de entrada/envio/controle, indicador com painel fechado, pausas amarelas estáticas, progresso desconhecido congelado, avisos verde/vermelho após reinícios, reconhecimento por Downloads e pelo clique no botão interceptado pela superfície nativa, prioridade de erro sobre transferências ativas, Mais, reorganização sobre o SVG, ambos os layouts, resize, abertura por atalho no Zen, consumo do clique externo, foco, rejeição de sessões/mensagens e passagem para Ferramentas. Parâmetros locais `slow` e `unknown` fornecem transferências demoradas/chunked determinísticas. `downloads` também confere a borda pausada restaurada antes de abrir o gerenciador. O documento auxiliar não recebe permissões para comandos do aplicativo.

`security-boundaries` exercita as restrições de documento/interface, comandos negados a sites e Ferramentas, bloqueio de navegação externa/novas janelas, tentativas de navegar para arquivos internos/locais, ações malformadas, parâmetros duplicados, tokens inválidos, sequências repetidas e sessões encerradas de painéis. `webview-runtime` simula versões do mecanismo por `config/runtime-fixture.json` exclusivamente no aplicativo isolado de testes; a produção ignora esse arquivo e não expõe comando de teste. Confere aviso, Depois, pendência nas configurações, outra versão, detecção indisponível, gravação de notas pendentes, revisão de formulário editado/download, cancelamento, falha ao reabrir e restauração do checkpoint. Na conclusão bem-sucedida, o executor de testes reabre o processo com o mesmo perfil; não instala um runtime da Microsoft nem verifica uma troca real de versão. A adoção efetiva de um mecanismo recém-instalado continua sendo uma verificação de release no Windows.

Antes das verificações nativas de arraste, redimensionamento e captura do PiP, o executor dá foco ao reprodutor flutuante verificado pela interface principal. Selecionar apenas seu documento no WebDriver não ativa a janela do Windows. As verificações de vínculo com a janela em primeiro plano continuam obrigatórias antes e durante a entrada do ponteiro; o pop-up não recebe permissões adicionais.


`new-tab` também verifica o deslocamento de 80 px para cima do conjunto da busca, espaçamento responsivo em janelas pequenas, favicons locais de 24 px, ícones genéricos, destinos exatos da última página e navegação por cartão em um painel do split sem foco. Um PNG gerado no servidor local exercita captura real de favicons no Windows e persistência; um favicon atrasado liberado após limpar o histórico não pode repovoar o cache. Abrir a página interna não faz requisição extra de favicon. Testes unitários cobrem migração idempotente, limites de 512 entradas/64 KiB, decodificação PNG, nova tentativa após falha de gravação, hosts/portas distintos e épocas antigas de captura. Os ícones são dados locais reconstruíveis e permanecem fora dos backups na versão 4.

`zoom` também exercita a barra com apenas o ícone e seu painel nativo: largura de 240 px, distância de 6 px do botão, páginas residentes visíveis, atualização pelo slider antes da soltura, valores antigos fora dos níveis padrão, falha SQLite injetada e nova tentativa, ações autenticadas, fechamento/foco, exclusão mútua com volume/privacidade, troca de foco na divisão, os dois layouts de abas e largura mínima da janela. Testes JavaScript cobrem agrupamento, entrega do último valor, captura da origem durante navegação, recuperação do estado confirmado e atualizações atrasadas da interface. A página auxiliar não recebe permissões de IPC da aplicação.

A validação local da interface de zoom em 3 de novembro de 2026 passou nas verificações consolidadas e nos cenários Windows `zoom`, `media-volume`, `privacy`, `split-tab-groups`, `keyboard` e `backup`. `tab-docking` não concluiu porque o WebView2 revogou a captura do ponteiro ao atravessar uma página nativa. A mesma falha foi reproduzida em um build isolado do commit anterior à mudança, `3977e0d`; esse cenário continua como limitação de validação neste ambiente. Suas verificações foram mantidas.

`split-tab-groups` verifica listas e seleção independentes, os dois botões de nova aba, escopo de Ctrl+Tab, transferência real entre barras, contextos antigos dos grupos, falha de gravação injetada, alinhamento do divisor em 20/50/80% nas larguras de 1160 px e mínima de 680 px, transições horizontal/vertical, preservação de formulários residentes, substituição da aba selecionada e restauração após reinício.

As verificações do cabeçalho conferem a ordem endereço/favoritos/abas dos painéis, a mesma instância da barra ao criar a divisão, toda a largura dos painéis, um único conjunto de controles da janela e um campo de endereço utilizável em 680 px. Exercitam Mais por mouse e teclado, passagem para diálogos sem revelar brevemente as páginas, acesso à Privacidade nativa, o limite de 1000/1001 px, troca de workspace, Zen e retorno à barra de abas comum no topo. Mudanças no cabeçalho devem preservar documentos, formulários, rolagem e histórico de navegação.

`tab-docking` envia movimentos e soltura reais do ponteiro dos dois layouts de abas, atravessando páginas nativas até as bordas da página. Verifica vínculo, visibilidade e ausência de ativação em primeiro plano da prévia, tamanho lógico/físico, estado inalterado durante a prévia, ambos os lados, substituição/troca, preservação de proporção e ordem das abas, Escape, falha SQLite injetada e nova tentativa, preservação de formulário/histórico/âncora de rolagem, transferência de workspace e restauração após reinício. O helper Windows inspeciona somente janelas do executável isolado verificado. Veja [visualização dividida](../features/split-view.md).

Mantenha cada travessia do arraste em uma sequência contínua de ações W3C do ponteiro. Enquanto o botão estiver pressionado, inspecione os limites nativos da janela sem trocar a WebView selecionada pelo WebDriver; mudar para o documento da prévia libera a captura do ponteiro e cancela corretamente o gesto. Inspecione seu documento somente após a soltura.

As páginas de encaixe dos testes informam a largura nativa da área visível e um histórico limitado de eventos de redimensionamento. Enquanto o mouse permanece pressionado na borda, `tab-docking` confere a largura final da companheira, a seleção/divisão confirmadas sem alterações e a continuidade da geometria da prévia durante outra gravação da sessão. Mover ao centro ou cancelar restaura as larguras anteriores. Redefinir o histórico de larguras antes de soltar verifica que a confirmação nunca expande a companheira entre a prévia e o layout confirmado. A cobertura inclui substituição, troca, ambos os layouts de abas, janelas redimensionadas e restauração após falha de persistência. Hibernar a companheira durante um gesto deve reservar seu painel sem recarregar; uma nova passagem pela borda também não deve carregá-la, e somente uma soltura confirmada com sucesso a acorda.

A regressão do cartão arrastado também verifica título/site nativos, afastamento do ponteiro, ausência de destaque de encaixe com uma aba e bloqueio de IPC da aplicação pela superfície auxiliar antes de iniciar a entrada do ponteiro. Arrastes reais devem manter o cartão visível sobre o centro da página nos dois layouts. A superfície cobre a área interna da janela principal para exibir cartão e destaque de encaixe juntos; na borda, somente a companheira residente permanece visível no painel planejado, enquanto os demais documentos continuam residentes e temporariamente ocultos.

`privacy` verifica o pop-up de 300 px abaixo do botão do escudo, controles independentes, rollback após falha de armazenamento, ações autenticadas, fechamento, resize, dois layouts de abas, preservação dos documentos na divisão, auto skip em segundo plano, origem do PiP e persistência após reiniciar. O [guia de auto skip](../features/auto-skip-ads.md) descreve as páginas locais com o controlador sem alterações e a verificação explícita do YouTube dependente de rede.

Os três cenários `persistence-*` injetam falhas SQLite no banco verificado do cenário isolado enquanto a aplicação está aberta. Conferem política/histórico do shield, exclusão/ativação transacional de workspace, substituição da divisão com limite de residentes, isolamento da prévia e rollback da proporção com medição da largura nativa dos painéis. Cada um remove seu trigger e tenta a operação novamente. Execute `npm run test:native -- --list` para consultar a lista atual de cenários. Veja as [correções de falhas](../reviews/2026-11-02/correctness-fixes.md).

`--case tab-churn` mantém dez abas abertas, executa vinte ciclos de criação/carregamento/fechamento, compara contagens estabilizadas de recursos nativos com as views residentes e verifica que a hibernação explícita chega a uma view. No Windows, amostra a árvore de processos descendentes da aplicação isolada, incluindo working set, bytes privados comprometidos, totais de CPU, handles e papéis identificados do motor. As linhas de comando completas dos processos não são salvas.

Para uma execução longa, use `node tools/testing/tab-churn.mjs 10` após a mesma preparação de build/drivers. O teste realiza dez ciclos por minuto durante o período solicitado (1–60 minutos), amostra a cada minuto e grava `artifacts/tab-churn.json` no diretório isolado. O cenário curto integra a suíte completa; a medição longa é explícita. Working set crescente exige investigação por processo/heap e isoladamente não comprova vazamento. Execute medições sequencialmente, com o desktop de teste disponível.

Operações em WebViews filhas consultam o handle e a URL esperados por até dez segundos, sem presumir que a WebView já exista quando o botão da interface muda. Consultas adicionais são registradas com o tempo decorrido. Essa sincronização cobre criação/navegação do pop-up; as asserções internas continuam verificando controles e dimensões reais.

Após compilar uma release de produção, execute `node tools/testing/release-metrics.mjs` para registrar revisão Git, versões das ferramentas, bytes brutos/gzip do frontend e bytes do executável nativo. São medições de artefatos, não benchmarks de RAM ou inicialização. Consulte [validação de desempenho](performance.md) para comparações. `npm run security:check` verifica caminhos rastreados/preparados, assinaturas comuns de segredos, regras de exclusão e espaços inválidos sem imprimir o conteúdo dos segredos.

Execute `--case media-mute` para atividade de áudio nativa, mute em segundo plano e valores iniciais após reiniciar.

`--case media-volume` mede o ganho de áudio artificial e verifica volume e fallback na navegação. Também exercita o pop-up de volume com o percentual abaixo do slider pelo identificador da sua própria WebView no WebDriver, verifica as dimensões de 200 × 64 px e a distância de 6 px abaixo do botão, alinhamento e atualização do percentual, setas do teclado, arraste pelo ponteiro, fechamento, reabertura rápida e os dois layouts de abas, e confirma que nem a página nem qualquer painel da divisão são ocultados ou recarregados. As verificações da WebView auxiliar selecionam temporariamente o documento empacotado e restauram o identificador da interface principal; não acrescentam permissões de IPC da aplicação. O helper de redimensionamento Windows altera somente a área cliente do executável isolado verificado, pois o redimensionamento pelo WebDriver pode afetar uma única WebView em vez da janela que a contém. Regressões JavaScript cobrem os limites da janela, preservação do arraste, agrupamento e envio do último valor ao fechar antes do próximo quadro de animação.

`--case media-pip` valida a detecção automática de vídeos sem abrir o volume nem solicitar um relatório manualmente, seleciona o maior vídeo elegível pelo botão da barra e verifica abertura/saída nos dois layouts e no painel focado da divisão. Também cobre o fechamento a partir de outra aba/workspace, fechamento externo, vídeos de outra origem e proteção da WebView de origem. Os comandos internos existentes mantêm a cobertura de documentos antigos, candidatos explícitos e players restritos. Regressões JavaScript verificam desempate estável na seleção, consultas compartilhadas, bloqueio de cliques repetidos e cancelamento quando o contexto focado muda durante uma consulta. O pop-up de volume não contém controles de Picture-in-Picture.

O cenário de PiP também seleciona o identificador WebDriver do player próprio e verifica uma trilha em movimento somente de vídeo, volume no hover, atualização imediata do percentual em 0%, 100% e 200%, ajuste por teclado, foco com Escape, sincronização com o volume nativo e frames de outra origem. Os vídeos sintéticos contêm trilhas de áudio geradas para exercitar a amplificação sem microfones nem mídia externa. Regressões do player cobrem a duração do hover/foco/arraste, confirmações antigas de volume e liberação somente das trilhas espelhadas ao fechar. Campos da sessão própria/nativa distinguem a janela da aplicação da alternativa nativa sem alterar os comandos de entrada/saída.

Depois que o PiP nativo fecha, o cenário ativa somente a janela Windows do aplicativo isolado verificado antes de conferir a retomada da detecção. O foco no DOM pelo WebDriver não garante que a janela do sistema operacional esteja em primeiro plano; as consultas periódicas são pausadas intencionalmente enquanto a aplicação está sem foco.

`--case media-pip-shadow` confere a opção de aparência desligada por padrão, busca traduzida nas configurações, alterações ao vivo sem substituir a sessão ou redimensionar sua área de vídeo, estado minimizado, outro workspace, continuidade do volume/reprodução e persistência após reiniciar. Os artefatos externos `pip-shadow-off.png` e `pip-shadow-on.png` incluem a sombra do Windows sobre o fundo do aplicativo isolado. A captura exige foco em primeiro plano, centraliza o player dentro da área interna principal isolada e verifica se os pontos amostrados pertencem somente a essas duas janelas verificadas antes e depois da cópia; regiões cobertas são rejeitadas. As imagens ficam no diretório ignorado de artefatos do cenário. Testes JavaScript cobrem armazenamento inválido, inicialização/alterações serializadas e reversão após falha nativa; testes Rust de backup cobrem campos ausentes em versões antigas e validação booleana estrita.

As verificações do player próprio conferem o layout de 400 × 225 px sem moldura, os controles SVG centralizados e o domínio de origem, capturam imagens com controles visíveis/ocultos e exercitam ocultação por inatividade, foco pelo teclado, visibilidade em pausa, arraste do cabeçalho, minimizar/restaurar e limites em janela pequena. O helper Windows da janela flutuante identifica somente o executável isolado exato e sua janela flutuante antes de inspecionar/restaurar ou testar arraste/redimensionamento nativo pelo ponteiro; a entrada exige foco em primeiro plano e um ponto dentro daquela janela verificada. Testes JavaScript usam um relógio controlado para verificar o prazo de dois segundos e suas exceções de foco, volume e arraste.

A regressão de mudanças de iframe remove um frame não relacionado enquanto outra aba está focada, deixando a chave agregada de mídia da origem invalidada. Ajustes comuns de volume devem rejeitar essa chave; o player flutuante só pode alterar o volume após conferir sua sessão de origem em relatórios novos. Os testes Rust cobrem a proteção da chave invalidada e a rejeição de documentos de origem, gerações e sessões antigos.

`--case media-pip-continuity` troca o recurso no mesmo elemento de vídeo, encerra uma trilha capturada e depois bloqueia a recaptura. Verifica substituição de trilha na janela existente, recuperação limitada, cópia sem áudio, restauração da imagem original, confirmação do último volume, aviso de falha e rejeição de sessão antiga após navegar. Regressões JavaScript também cobrem buffering, pausa, busca e callbacks de documentos removidos. O cenário principal de PiP confere a linha transparente de volume de 120 × 28 px, ausência de fundo/borda/sombra, distância de 6 px à esquerda do alto-falante, alinhamento do percentual à esquerda da barra, largura fixa do percentual, área de interação de 28 px e espaço em relação ao tempo. Os valores de 0%, 100% e 200% devem preencher 0%, 50% e 100% da barra.

`--case media-pip-fps` grava localmente vídeos artificiais finitos de 30/60 FPS e mede cada um por dez segundos com a imagem de origem visível, oculta e em uma aba em segundo plano. Exige pelo menos 90% da taxa de apresentação esperada e nenhuma pausa acima de 250 ms, gravando as medições em `artifacts/pip-fps.json`. A gravação dos testes usa somente conteúdo gerado em canvas. Mudanças de fonte, buffering ou reinício dos contadores invalidam a amostra; verificações no YouTube devem aguardar a estabilização e reiniciar amostras entre anúncios. Verificar somente que chegaram novos quadros não comprova a qualidade da taxa de quadros.

Depois da compilação isolada e da configuração do driver, `npm run test:native:youtube` executa explicitamente uma verificação do YouTube dependente de rede, fora dos cenários locais. Reinicia amostras após mudanças de fonte/buffering, exige duas amostras estáveis de dez segundos com pelo menos 90% do FPS entregue pela origem e intervalos de até 250 ms, confere o volume compacto e a restauração da imagem original, e preserva `artifacts/youtube-fps.json` com uma captura de tela. Informa as transições de fonte observadas; os anúncios são controlados pelo YouTube e podem não aparecer em uma execução. O cenário local de continuidade cobre a troca de fonte de forma determinística, independentemente da disponibilidade de anúncios.

O cenário `new-tab` exercita a página interna sem internet, foco inicial no campo central, cinco sites recentes distintos além do primeiro lote do histórico, preservação de rascunho, limpeza do histórico, falha de leitura e nova tentativa, navegação autenticada após retornar pelo histórico nativo, voltar/avançar/recarregar, isolamento dos painéis do split, largura mínima, ambos os layouts, Tab e Ctrl+L com entrada real do Windows, reabertura de guia fechada, hibernação, restauração de sessão nomeada e reinício. Testes unitários cobrem domínios permitidos, termos codificados, respostas antigas de documentos/solicitações, atualização em segundo plano durante navegação aceita e renderização segura de texto. Usa somente histórico artificial e destinos locais. O harness seleciona explicitamente a interface principal entre os WebViews locais e ativa a janela de teste verificada antes de conferir quem está em primeiro plano; teclas injetadas sempre são liberadas na limpeza.

O cenário `titlebar-actions` usa entrada real do ponteiro para verificar a espera de meio segundo, o marcador de inserção, as duas direções de arraste, cancelamentos, bloqueio de movimento antecipado e cliques rápidos nos atalhos visíveis, incluindo QR Code. Ele confere que os arrastes nos layouts horizontal e vertical preservam a posição da janela nativa, favoritos ocultos mantêm sua posição salva, a ordem permanece após reiniciar e o modo compacto mantém o menu existente. Execute `npm run test:native -- --case titlebar-actions` após compilar o aplicativo isolado.

O cenário `ephemeral-cleanup` verifica a exclusão após o fechamento individual e em lote de abas hibernadas, a preservação durante a hibernação e a limpeza de um diretório residual isolado na inicialização.
